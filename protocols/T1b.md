# T1b — бенч 4 параллельных воркеров (исправление T1)

Дата: 2026-11-01. Прогон выполнен на закрытом внутреннем стенде. Модель qwen3:4b-instruct.

## Суть теста
T1: бенч одним потоком → целевой парсер не извлёк ни одного item, большинство слотов
инференса простаивали.
T1b: те же условия + **4 параллельных воркера** (`concurrent.futures.ThreadPoolExecutor(4)`
поверх urllib), 40 звонков (страта: средние 2000–5000 зн. + короткие <2000),
исправленный парсер, динамический JSONL.

## Подготовка
- Выделенный инстанс инференса поднят на локальном интерфейсе выделенного порта;
  изоляция от параллельных прогонов проверена (посторонних подключений нет,
  бенч гонялся локально на стенде).
- `OLLAMA_NUM_PARALLEL=4`, `OLLAMA_MAX_LOADED_MODELS=1`, keep_alive -1.
- Прогрев модели до полного размещения на GPU перед стартом.

## Методика измерений
- Скользящие 10-минутные окна пропускной способности на устаканившемся участке
  (окна хвостового выброса не считаются: там пул догоняет последние звонки).
- Фактическая скорость: число звонков / время прогона.
- Качество парсинга: доля strict-парсинга JSON, доля schema-fail, доля quote-miss.
- Ресурсы: пиковое потребление VRAM, загрузка GPU.

## Диагностика парсера (корень отказа T1)
1. В T1-скрипте в запросе не было `format`-схемы (в протоколе T1 заявлена — фактически
   отсутствовала): модель отвечала без гарантированного JSON, а ответ обрезался лимитом
   генерации → `extract` давал 0 items на всех звонках.
2. Отладка на 1 звонке: с `format`-схемой модель возвращает чистый JSON в
   `message.content` (без markdown-обрамления, без `<think>`).
3. Вторая находка: слишком малый лимит генерации при полном промпте (system + транскрипт)
   обрезал JSON → парс падал. После поднятия лимитов генерации и контекста —
   все ответы strict-парсятся.
4. Модель иногда дублирует пункты: парсер дедуплицирует по id (первое вхождение,
   диапазон 1–54) — во всех ответах ровно 54 items.

## Исправления T1b-скрипта
- `format`: схема checklist в каждом запросе;
- `options`: увеличенные лимиты генерации и контекста, `temperature 0.1`;
- парсер: strict `json.loads` → срез ```-забора → regex `{.*}` → посимвольный salvage
  обрезанного JSON; дедупликация id 1–54;
- `ThreadPoolExecutor(4)`, аппенд JSONL под локом, `ts_epoch` в каждой строке.

## Ход прогона
Прогон контролировался по монитору (done-счётчик, GPU, VRAM, schema_fail); завершён
естественно по исчерпании списка звонков, без принудительной остановки.

## Итоги (детальные числа — на закрытом стенде)
- Готово: 40/40, ошибок HTTP 0.
- Парсер: все ответы strict, во всех строках ровно 54 items; schema-fail = 0 %.
- quote-miss: доли процента по всем строкам; единичные звонки с промахами.
- Пропускная способность: скользящие 10-мин окна на устаканившемся участке —
  устойчиво выше целевого порога; параллелизм на 4 воркерах дал кратный прирост
  относительно однопоточного T1.
- Ресурсы: пик VRAM в пределах лимита стенда; после остановки инстанса память освобождена.

## Вердикт: СДАН
- скользящие 10-мин окна на устаканившемся участке ≥ целевого порога ✓
- VRAM в пределах лимита стенда ✓
- schema-fail < 5 % (0 %) ✓
Против T1: кратный прирост скорости, парсер исправлен (0 items → 54/54 strict
на всех звонках).
